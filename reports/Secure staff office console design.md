# Build the office console behind four locks

Farbaek should build `office.farbaek.com` as its own Railway service, and every page, Server Action and Route Handler on it should independently check four things on the server: that the request arrived on the office host with an office-only `__Host-` cookie; that the Supabase session is at `aal2` with a recent second factor; that a server-only `staff_members` row, re-read from the database on each request and never trusted from the JWT, grants that role the action with whatever reason, cap or expiry it requires; and that the action is written to an append-only, hash-chained staff audit log before the response returns. This matters now because today's read-only `/admin` console ([ADR 0026, 2026-10-18](../docs/adr/0026-admin-console.md)) is gated only by an email allowlist and a magic link, which NIST SP 800-63B-4 and OWASP treat as no stronger than the mailbox behind it; the moment the console can extend trials, grant credits, suspend accounts, take down sites or flip kill switches, that gate becomes the weakest point in the company. October 2026 platform facts shape the details: Supabase TOTP MFA is generally available and free, but passkeys entered beta only on 2026-05-28 and WebAuthn as a second factor is still experimental, so TOTP is the mandatory floor today; Supabase's own session time-box and idle timeout need the Pro plan and only bite on token refresh, so the console must enforce its own 12-hour absolute and 15-to-30-minute idle limits; and Railway Hobby allows two custom domains per service, both already used on the main service, which makes a second service the cleanest home for the office host. Roles should stay few (owner, admin, support, trust and safety, viewer) with conditions instead of new roles, two-person approval reserved for slow, irreversible actions, and kill switches kept single-person and alerted. The first controls worth building are customer search and a customer page, suspend and restore with reasons, quarantine-first site takedown with notices, audited credit and trial adjustments, named kill switches with honest in-app messages, and cost and health tiles labelled as estimates, all inside a calm UI (dimmed sidebar, Cmd+K, entity timelines, friction graded by risk) that respects Farbaek's White Signal rules.

## Five fixed roles with conditions beat a role for every job

No company I could find publishes its internal staff permission matrix, including GitHub, Stripe, Shopify, Intercom, Vercel and Supabase, but what is public converges. OWASP says to deny by default, check permissions on every request on the server, and review periodically for "privilege creep"; it warns that pure role-based models cause "role explosion" and handle object-level decisions poorly, and prefers attribute conditions such as time or device ([OWASP Authorization Cheat Sheet, undated, accessed Oct 2026](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)). Stripe's published Dashboard catalogue shows narrow roles at scale: roughly two dozen tightly scoped roles, **exactly one Account Owner** who alone can close the account or transfer ownership, an IAM Administrator who cannot grant Admin, and an explicit warning that any role able to invite users lets an attacker who compromises it "invite additional users under their control" ([Stripe Docs: User roles, undated, accessed Oct 2026](https://docs.stripe.com/get-started/account/teams/roles)). NIST SP 800-53 AC-6(2) adds that privileged users should use non-privileged accounts for everyday work ([NIST AC-6 via csf.tools, Rev 5](https://csf.tools/reference/nist-sp-800-53/r5/ac/ac-6/)), which Google turns into practice by giving each super admin a separate admin account, "each managed by a separate individual (avoid sharing an admin account)" ([Google Workspace admin security best practices, undated](https://knowledge.workspace.google.com/admin/users/security-best-practices-for-administrator-accounts)).

For Farbaek that means **five fixed roles plus attribute conditions** (a reason, a ticket reference, an amount cap, a consent flag, a time window), with a Finance role kept locked until `docs/billing/go-live.md` is complete. The matrix below is a synthesis, not a copy of any company's. Key: **Y** allowed; **R** allowed with a required reason and ticket or case reference, logged; **2P** needs a second person's approval; **JIT** only during a time-boxed elevation; **N** never in the console.

| Action | Owner (CEO) | Admin | Support | Trust and safety | Viewer |
|---|---|---|---|---|---|
| View account metadata (plan, trial, usage totals) | Y | Y | Y, email masked | Y | Y, masked |
| View private content (projects, prompts, generated code) | R | R | R plus ticket or customer consent | R, open abuse case | N |
| View secret values (keys, tokens, env values) | N, fingerprint only | N | N | N | N |
| Read-only "view as" | R | R | R plus consent, 15 min | R | N |
| Suspend or restore an account | R | R | Request only | R | N |
| Take down a published site | R | R | N | R | N |
| Extend an internal trial | R | R, within cap | R, one small extension | N | N |
| Grant usage credits | R | R under threshold, 2P above | N | N | N |
| Per-workspace feature flag | Y | R | N | N | N |
| Global kill switch | R, instant alert | JIT plus R, instant alert | N | JIT for abuse switches | N |
| Invite staff or change staff roles | Y with step-up | Request only | N | N | N |
| Change or remove an owner | 2P with step-up, never the last owner | N | N | N | N |
| Bulk export of customer data | 2P | 2P | N | N | N |
| Change audit retention or alerting | 2P | N | N | N | N |
| Read the staff audit log | Y | Y | Own actions | Own actions | Y, read-only |
| Billing state, refunds | Locked while `not_connected`, then 2P | N | N | N | N |

Separation of duties has to be scaled honestly for a one-to-ten person team. NIST AC-5 allows **compensating controls such as additional auditing** where full separation is impractical ([NIST AC-5 via csf.tools, Rev 5.2.0](https://csf.tools/reference/nist-sp-800-53/r5/ac/ac-5/)), and AC-3(2) on dual authorization warns that two-person control must be weighed against cases needing an immediate response ([NIST AC-3(2) via csf.tools](https://csf.tools/reference/nist-sp-800-53/r5/ac/ac-3/ac-3-2/)). That supports a clear split. Two-person approval belongs only on slow, high-impact, hard-to-reverse actions: admin or owner role changes, bulk exports, audit configuration, large credit grants, data deletion and, later, money. Kill switches stay single-person, reason-required, instantly alerted to the owner and reviewed afterwards, because a safety switch that needs two people at 3 a.m. is a dead end. When the owner is the only senior person, the honest compensating control is self-approval after a cooling-off delay, an immediate notification and a mandatory next-day review, never a silent bypass.

Just-in-time elevation gives admins dangerous powers without standing rights. Google Cloud's Privileged Access Manager is the clearest reference: each entitlement defines who may request, whether a justification is required, the maximum grant duration, approvers and notified stakeholders; **roles are revoked automatically at expiry**, pending requests lapse after 24 hours, and grant events stay in audit logs ([Google Cloud PAM overview, last updated 2026-10-13](https://docs.cloud.google.com/iam/docs/pam-overview)). No standard sets a JIT or break-glass duration (the vendor figures I found were unverified), so a 1-to-4-hour cap is a judgement call. Practitioner guidance names the classic failure, emergency accounts left permanently enabled ([hoop.dev on break-glass access, undated](https://hoop.dev/blog/what-break-glass-access-really-means/)), and NIST AC-2(2) requires temporary and emergency accounts to disable automatically ([NIST AC-2 via csf.tools](https://csf.tools/reference/nist-sp-800-53/r5/ac/ac-2/)). Store `expires_at` on the server and check it on every request.

Owner continuity needs code, not just policy. GitHub recommends "at least two people within each organization have the owner role" and prevents people changing their own role ([GitHub Docs: Maintaining ownership continuity, undated](https://docs.github.com/en/organizations/managing-peoples-access-to-your-organization-with-roles/maintaining-ownership-continuity-for-your-organization)); GitLab merged code that blocks deleting the last organization owner ([GitLab MR 249299](https://gitlab.com/gitlab-org/gitlab/-/merge_requests/249299)); and Google advises keeping a super admin's security key somewhere safe at your physical location, with last-resort recovery resting on DNS ownership ([Google Cloud super admin best practices, undated](https://docs.cloud.google.com/resource-manager/docs/super-admin-best-practices)). Farbaek's version is a SQL invariant inside the role-change `app_*` function that refuses any change leaving zero active owners or letting an owner demote themselves; owner-only role changes with step-up; a rule that admins cannot suspend, demote, reset MFA for or end sessions of an owner; a sealed break-glass owner identity whose hardware key is stored offline and whose use alerts and is logged as break-glass; and a recovery runbook outside the app covering the Supabase dashboard and DNS, because a console cannot recover itself. ADR 0026 names `hello@farbaek.com` as the admin sign-in. If that mailbox is or becomes shared, it is exactly the shared admin account Google warns against, so staff identities should be named individuals.

## Every staff request must prove aal2 in server code, not only in RLS

### TOTP is the floor today, phishing-resistant keys arrive when Supabase stabilizes them

The authorities agree that FIDO2/WebAuthn is the only widely available phishing-resistant MFA. NIST SP 800-63B-4 (final, July 2025) requires that verifiers "SHALL offer at least one phishing-resistant authentication option at AAL2", states that "OTP authentication is not phishing-resistant", bars email for out-of-band authentication, and allows synced passkeys only up to AAL2 because AAL3 needs a non-exportable key ([NIST SP 800-63B-4, July 2025](https://pages.nist.gov/800-63-4/sp800-63b.html); [CSRC publication record](https://csrc.nist.gov/pubs/sp/800/63/4/final)). CISA "strongly urges system administrators and other high-value targets" to migrate, calls app-based OTP the best interim option for small businesses, and treats SMS as a last resort; I found no newer CISA document superseding this October 2022 fact sheet ([CISA fact sheet, Oct 2022](https://www.cisa.gov/sites/default/files/publications/fact-sheet-implementing-phishing-resistant-mfa-508c.pdf)). OWASP says "Require MFA for administrative or other high privileged users" and notes that a passkey touch confirming presence alone "is not a second factor", so user verification must be checked server-side ([OWASP MFA Cheat Sheet, undated, accessed Oct 2026](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html)).

Supabase's October 2026 state sets the practical ceiling. **TOTP is free and enabled on every project by default** ([Supabase TOTP guide, accessed Oct 2026](https://supabase.com/docs/guides/auth/auth-mfa/totp)). Phone MFA is a paid add-on at **$75 a month for the first project** and $10 for each additional one, plus SMS provider fees ([Supabase Advanced MFA Phone, accessed Oct 2026](https://supabase.com/docs/guides/platform/manage-your-usage/advanced-mfa-phone)). First-factor passkeys entered beta on 2026-05-28 behind `auth: { experimental: { passkey: true } }`, with an API that "may change without notice during the beta phase" ([Supabase changelog: Passkeys (Beta), 2026-05-28](https://supabase.com/changelog/46458-passkeys-for-supabase-auth-beta)). WebAuthn as a second factor exists only as an experimental client namespace ([Supabase Swift MFA reference, accessed Oct 2026](https://supabase.com/docs/reference/swift/auth-mfa-api)), and recovery codes are experimental too, returned in plaintext "exactly once" ([supabase-js recoveryCodes.generate, accessed Oct 2026](https://supabase.com/docs/reference/javascript/auth-mfa-recovery-codes-generate)). No source says whether a beta passkey sign-in yields `aal1` or `aal2`, so that must be tested on staging before any rule depends on it.

The defensible posture is mandatory TOTP for every staff member now, **two enrolled factors per person** (two authenticator apps) in place of recovery codes, and lost-factor recovery through a second admin who calls the service-role `auth.admin.mfa.deleteFactor` after an out-of-band identity check such as a video call, with the reset logged ([supabase-js GoTrueAdminApi source](https://raw.githubusercontent.com/supabase/supabase-js/master/packages/core/auth-js/src/GoTrueAdminApi.ts)). Hardware keys for the CEO and admins, with a spare each, follow once Supabase marks WebAuthn stable. Never offer staff self-service email-based MFA reset, since OWASP says recovery must not "provide an attacker with a way to bypass MFA". The residual risk, a real-time phishing relay of password and TOTP code together, is the one only WebAuthn (or an outer gate that uses it) removes.

### Service-role writes bypass RLS, so the claim check belongs in code

Supabase carries MFA state in the JWT: `aal` is `aal1` or `aal2`, and `amr` is an array of `{method, timestamp}` entries ordered most recent first. The documented RLS pattern is a RESTRICTIVE policy, `(select auth.jwt()->>'aal') = 'aal2'`, so permissive policies cannot outweigh it ([Supabase MFA guide, accessed Oct 2026](https://supabase.com/docs/guides/auth/auth-mfa)). Two Farbaek specifics follow. Staff-only tables should use the "enforce for all users" form, not the opted-in variant, under which an account with no enrolled factor passes at `aal1`. More importantly, that policy protects only reads made with a user's JWT: Farbaek's writes go through service-role `app_*` functions, and **the service role bypasses RLS**. Every office Server Action and Route Handler must therefore call `getClaims()` itself, which verifies locally against the project JWKS when asymmetric keys are used ([supabase-js getClaims, accessed Oct 2026](https://supabase.com/docs/reference/javascript/auth-getclaims)), refuse anything below `aal2`, and pass the verified actor id and assurance level into the SQL function for the audit row. Next.js makes the same point from its side: Server Functions are POSTs to the page route, a matcher change "can silently remove Proxy coverage", so "always verify authentication and authorization inside each Server Function" ([Next.js proxy.js reference, updated 2026-09-04](https://nextjs.org/docs/app/api-reference/file-conventions/proxy)). Role claims added by the Custom Access Token hook are only as fresh as the token, one hour by default ([Supabase Custom Access Token hook, accessed Oct 2026](https://supabase.com/docs/guides/auth/auth-hooks/custom-access-token-hook)), so they serve routing and UI only; the database row decides, which makes revocation immediate and failure closed.

### Sessions need their own limits because Supabase's apply late or cost extra

Supabase access tokens default to one hour and refresh tokens are single-use with reuse detection that revokes the whole session, but **time-boxed sessions, inactivity timeout and single-session-per-user are "only on Pro Plans and up"**, they apply at refresh so "effective session duration equals the configured timeout plus the JWT expiry time" ([Supabase Sessions guide, accessed Oct 2026](https://supabase.com/docs/guides/auth/sessions)), and access tokens of revoked sessions "remain valid until their expiry time" ([Supabase Signing out guide, accessed Oct 2026](https://supabase.com/docs/guides/auth/signout)). Pro starts at $25 a month ([Supabase pricing, accessed Oct 2026](https://supabase.com/pricing)). NIST supplies the targets: at AAL2 an overall timeout of no more than 24 hours and inactivity of no more than one hour; at AAL3 an overall timeout that "SHALL be no more than 12 hours" and inactivity of no more than 15 minutes; and cookie expiry "SHALL NOT be relied upon" to enforce either ([NIST SP 800-63B-4 §2 and §5.1, July 2025](https://pages.nist.gov/800-63-4/sp800-63b.html)).

Whatever the Supabase plan, the console should enforce staff policy itself on every privileged request. It rejects sessions whose first-factor `amr` timestamp is older than **12 hours**; keeps a `staff_sessions` row keyed by the JWT's `session_id` with `last_seen_at` and rejects after **15 to 30 minutes idle**, which also gives admins an instant revoke switch; confirms for high-risk actions that the `session_id` still exists in `auth.sessions`, Supabase's documented signed-out check; and keeps one session per staff member by calling `auth.admin.signOut(jwt, 'others')` right after each staff `aal2` sign-in. Supabase Pro is still worth raising with the owner when the console ships, because it also adds leaked-password protection and seven days of auth logs instead of one hour, but under the repo's rules that is the owner's money decision.

### Step-up means a fresh second factor bound to the specific action

Supabase has no built-in "verified within N minutes" primitive, so `amr` timestamps are the building block. For a Tier 3 action such as a role grant, bulk export, data deletion or, later, a refund, the Server Action looks for the newest `totp` entry in `amr` and requires it to be under about five minutes old; otherwise it returns a "confirm with your authenticator" state, the client runs `mfa.challenge()` and `mfa.verify()`, and the request retries. The confirmation should be bound to that exact action by hashing its payload with Farbaek's existing approval binding in `src/core/trust/`. OWASP supports both halves: re-authenticate before high-risk actions with "an authenticator already bound to the account", and for factor changes "do not rely solely on the active session, as it may be hijacked" ([OWASP Authentication Cheat Sheet, accessed Oct 2026](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html); [OWASP MFA Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html)). Two caveats apply: MFA challenge and verify are rate-limited at **15 per minute per IP, not configurable** ([Supabase Auth rate limits, accessed Oct 2026](https://supabase.com/docs/guides/auth/rate-limits)), and I could not confirm that `mfa.verify()` on an already-`aal2` session refreshes the `totp` timestamp, which needs a staging test before the pattern ships.

### Invite-only staff, one-step revocation and an app-level lockout

Staff authority lives in a server-only `staff_members` table with no RLS INSERT or UPDATE policy, so no user JWT can write it, and staff status is never derived from user-editable `user_metadata` or from an email domain alone. Onboarding starts with the owner, at `aal2` with step-up, creating an expiring `staff_invites` row through an `app_*` function; the invitee's verified email must match it, and the role activates only after they enroll and verify an MFA factor and complete an `aal2` sign-in. An existing customer account with the same email is never silently promoted. Supabase's Before User Created hook, available on Free and Pro, can deny sign-ups by rule if the office ever needs that ([Supabase Before User Created hook, accessed Oct 2026](https://supabase.com/docs/guides/auth/auth-hooks/before-user-created-hook)). Offboarding is a single use case: deleting the `staff_members` row takes effect immediately because every request re-reads it, after which the use case revokes the person's `staff_sessions`, bans the Auth user with `ban_duration: '876000h'` if they have no customer account to keep ([supabase-js GoTrueAdminApi source](https://raw.githubusercontent.com/supabase/supabase-js/master/packages/core/auth-js/src/GoTrueAdminApi.ts)), removes their factors, and records the rotation of any shared secrets they could see. Supabase's security notification emails, announced 2025-11-11, can tell staff when a factor is enrolled or removed or a password changes, once enabled per project ([Supabase changelog, 2025-11-11](https://supabase.com/changelog/40349-notify-users-about-security-sensitive-actions-on-their-accounts)).

Supabase's own rate limits are per IP and coarse, the account-level MFA and password attempt hooks require the **Team plan at $599 a month** ([Supabase Auth Hooks overview, accessed Oct 2026](https://supabase.com/docs/guides/auth/auth-hooks)), and auth audit logs keep **one hour on Free and seven days on Pro** ([Supabase pricing](https://supabase.com/pricing)). The console therefore needs its own per-account limiter, because OWASP says failed-login counters "should be associated with the account itself, rather than the source IP address" (for example, a pause after five failures in 15 minutes with growing delays, never a permanent lock); its own append-only staff sign-in log; and its own new-device alert to the staff member and the owner with time, browser and approximate location, as OWASP suggests, since I found no Supabase-native new-device notification.

### IP allowlists are a risk signal, an identity-aware proxy is the real outer gate

Railway's official account wrote on 2026-05-01 that "We do not offer built-in inbound IP allowlisting at the platform level" ([Railway Station, 2026-05-01](https://station.railway.com/questions/railway-ip-address-restrictions-7ddb0025)). Its docs name `X-Real-IP` as the client IP header ([Railway specs and limits, accessed Oct 2026](https://docs.railway.com/networking/public-networking/specs-and-limits)), but staff answers on its forum contradict each other about which `X-Forwarded-For` entry to trust, and one says no stable trusted-proxy range is published ([Railway Station thread, accessed Oct 2026](https://station.railway.com/questions/need-authoritative-railway-client-ip-p-b7a7b4bd)). MDN warns that when a server can be reached directly, "no part of the X-Forwarded-For IP list can be considered trustworthy" ([MDN X-Forwarded-For](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Forwarded-For)); OWASP treats IP and location as "risk signals, not as substitutes for authentication"; and ASVS 5.0 requirement 8.4.2 says network location must not be the only factor protecting admin interfaces ([OWASP ASVS 5.0 V8](https://raw.githubusercontent.com/OWASP/ASVS/master/5.0/en/0x17-V8-Authorization.md)). A new IP, country or device should therefore trigger step-up and an alert, never allow or deny on its own.

The stronger optional layer is **Cloudflare Access, free for up to 50 users** with 24 hours of log retention ([Cloudflare Zero Trust plans, accessed Oct 2026](https://www.cloudflare.com/plans/sase-zero-trust.md)). It is only real if the origin validates the `Cf-Access-Jwt-Assertion` header on every request against the team's rotating certificates, the application's AUD tag and the issuer ([Cloudflare: Validate JWTs, updated 2026-05-06](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/)), and if the service's `*.up.railway.app` domain is removed so traffic cannot go around Cloudflare. Access's email one-time PIN is a coarse outer gate, not an MFA factor; its value is hiding the console's login surface from the internet and from credential-stuffing bots, and, by my inference rather than any vendor claim, bringing phishing resistance early if its identity provider requires security keys. Tailscale's free tier is limited to non-commercial use, so it does not fit a company console ([Tailscale pricing, accessed Oct 2026](https://tailscale.com/pricing)).

## A second Railway service gives the office its own blast radius

### Railway Hobby is full, so the office needs a service, a plan or a wildcard

Railway's docs limit custom domains to **1 on Trial, 2 per service on Hobby and 20 per service on Pro** ([Railway docs: Working with Domains, undated, accessed Oct 2026](https://docs.railway.com/networking/domains/working-with-domains)). Railway's official account confirmed on 2026-06-18 that the Hobby limit is "per service, not per workspace or per project" and that one wildcard "would cover all subdomains and count as just 1 custom domain" ([Railway Station, 2026-06-18](https://station.railway.com/questions/custom-domain-maximum-number-a04e6013)); the wildcard rule rests only on that reply, and the pricing page's listing of 0 domains on Free contradicts a January 2026 staff post ([Railway pricing, accessed Oct 2026](https://railway.com/pricing)). Farbaek's production service already holds `www.farbaek.com` and `*.farbaek.si`, the latter recorded as "the plan's last custom domain slot" ([`docs/stages/stage-6.md`, 2026-10-20](../docs/stages/stage-6.md)). That leaves three options.

| Option | What changes | Cost and risk |
|---|---|---|
| (a) Second service from the same repo | Office build ships only office routes, with its own two domain slots, env vars and logs | Usage only: about $5 a month for 0.5 GB of RAM at Railway's $10 per GB-month, plus CPU (arithmetic on published rates, not a measurement); a second deploy to keep in step |
| (b) Upgrade the workspace to Pro | 20 slots per service, so office can share the main service | $20 a month per workspace including $20 of usage, versus Hobby's $5 ([Railway plans, accessed Oct 2026](https://docs.railway.com/reference/pricing/plans)); office code runs in the customer process |
| (c) Replace `www.farbaek.com` with `*.farbaek.com` | One slot covers www and office | Every name under farbaek.com reaches the app, so the proxy must refuse unknown hosts; shared blast radius |

**Option (a) is the recommendation.** On a shared deployment the proxy would rewrite `office.*` to an office segment and refuse it elsewhere, but that segment would still ship in the same build and process as the customer app and its in-process agent runs, so a dependency compromise or auth bug on the customer side would run beside staff code. Next.js itself recommends proxy "as a last resort" ([Next.js proxy.js reference, updated 2026-09-04](https://nextjs.org/docs/app/api-reference/file-conventions/proxy)) and stresses that a Server Action is "reachable via a direct POST request, not just through your application's UI" ([Next.js Data Security guide, updated 2026-10-06](https://nextjs.org/docs/app/guides/data-security)). A separate build means office code is absent from the customer server rather than merely refused there. The office service could also use Railway's Serverless sleeping, at the cost of a cold boot and a possible 502 on the first request after five to ten idle minutes ([Railway docs: Serverless, accessed Oct 2026](https://docs.railway.com/reference/app-sleeping)). Either way, the office proxy serves office routes only when `host` is exactly `office.farbaek.com`, matching how `src/proxy.ts` already routes on `host`, and the current `/admin` segment on www, which today's session path list covers, should stop being served there once the office host exists.

### Host-only cookies isolate sessions, but not against cookie tossing

`@supabase/ssr` sets no `Domain` by default, with `path: "/"`, `sameSite: "lax"`, `httpOnly: false` and a 400-day `maxAge` ([supabase/ssr constants.ts, main branch, accessed Oct 2026](https://raw.githubusercontent.com/supabase/ssr/main/src/utils/constants.ts)), so office and www cookies are already host-only: "the cookie is returned only to the host that sent it" ([MDN Set-Cookie, accessed Oct 2026](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)). Host-only scoping does not stop a compromised sibling from planting a same-named cookie on the parent domain. GitHub documented this "cookie tossing" in 2013 as one reason Pages moved to github.io, noting that the order in which same-named cookies are sent "is not specified by RFC 6265" ([GitHub blog: Yummy cookies across domains, 2013-04-09, updated 2019-01-04](https://github.blog/engineering/infrastructure/yummy-cookies-across-domains/)). The fix is a **`__Host-` prefixed cookie name**, which browsers reject if it carries a `Domain` attribute or lacks `Secure` and `Path=/`, set through `cookieOptions: { name: "__Host-<office>", secure: true, path: "/", sameSite: "lax" }` in every office Supabase client ([supabase/ssr createServerClient.ts](https://raw.githubusercontent.com/supabase/ssr/main/src/createServerClient.ts)), plus `httpOnly: true` if testing shows server-only auth works with it. Never set `Domain=farbaek.com` on www cookies, which would hand customer sessions to every subdomain and turn any subdomain takeover into session theft; MDN's takeover guidance is to create DNS records last when provisioning and remove them first when tearing down ([MDN: Subdomain takeover](https://developer.mozilla.org/en-US/docs/Web/Security/Attacks/Subdomain_takeover)).

### Same-site siblings need an Origin check and an office-only header set

`www.farbaek.com` and `office.farbaek.com` are "same-site but cross-origin" ([web.dev: same-site and same-origin](https://web.dev/articles/same-site-same-origin)), so SameSite cookies do nothing against a form POST from www, or a compromised sibling, to office. Next.js protects Server Actions by comparing the `Origin` host with the app's host, but "a request that carries no `Origin` header at all is allowed through with a warning" ([Next.js serverActions config, updated 2026-08-26](https://nextjs.org/docs/app/api-reference/config/next-config-js/serverActions)), and the docs list that check for Server Actions only. The office proxy should therefore require, on every non-GET request, `Origin` equal to `https://office.farbaek.com` or `Sec-Fetch-Site: same-origin` when `Origin` is missing, refusing requests with neither, while `allowedOrigins` stays empty and never includes `*.farbaek.com`.

A fully dynamic office makes a nonce CSP free, while keeping it off www matters because "Partial Prerendering (PPR) is incompatible with nonce-based CSP" ([Next.js CSP guide, updated 2026-03-20](https://nextjs.org/docs/app/guides/content-security-policy)). Today's `next.config.ts` sends a frame-ancestors-only CSP, `strict-origin-when-cross-origin` and HSTS with `includeSubDomains` to every non-preview host. The office set should tighten that as follows.

| Header | Office value | Why |
|---|---|---|
| `Content-Security-Policy` | Nonce `script-src` with `'strict-dynamic'`, `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'` | Next.js nonce pattern; the office is dynamic anyway |
| `Referrer-Policy` | `no-referrer` | Internal URLs with ids never reach outside links ([MDN Referrer-Policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Referrer-Policy)) |
| `Cross-Origin-Opener-Policy` and `-Resource-Policy` | `same-origin` and `same-origin` | Blocks window-handle leaks; stricter than OWASP's general `same-site` because www is same-site ([OWASP HTTP Headers Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html)) |
| `Cache-Control` | `no-store`, including Route Handlers | Supabase says never ISR on auth routes ([Supabase advanced SSR guide](https://supabase.com/docs/guides/auth/server-side/advanced-guide)) |
| `X-Robots-Tag` | `noindex, nofollow` | See the next subsection |
| `Strict-Transport-Security` | `max-age=63072000`, sent by office itself | www's `includeSubDomains` covers only `*.www.farbaek.com` ([MDN HSTS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Strict-Transport-Security)) |
| `X-Frame-Options`, `X-Content-Type-Options`, `Permissions-Policy` | `DENY`, `nosniff`, deny camera, microphone, geolocation, payment, USB | Keep the baseline, widened |

HSTS preload should wait: it "applies to all subdomains, including internal subdomains" and "cannot easily be undone" ([hstspreload.org, accessed Oct 2026](https://hstspreload.org/)), and it would require the apex to serve HSTS while the apex is currently a Spaceship URL redirect.

### The hostname will be public within an hour of its certificate

Certificate Transparency logs are "append-only ledgers of certificates… anyone can query them" ([certificate.transparency.dev](https://certificate.transparency.dev/howctworks/)); Chrome, Safari and recent Firefox require CT for publicly trusted certificates ([MDN: Certificate Transparency](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Certificate_Transparency)); and Railway issues certificates within about an hour of DNS updating. **Treat `office.farbaek.com` as public**, because its secrecy is not a control. Send `X-Robots-Tag: noindex` on every office response, including sign-in and error pages, and keep the host out of www's robots.txt, which is itself public. Google says robots.txt "is not a mechanism for keeping a web page out of Google" and that a blocked crawler "will never see the `noindex` rule" ([Google Search Central: noindex, updated 2025-12-10](https://developers.google.com/search/docs/crawling-indexing/block-indexing); [robots.txt intro, updated 2025-12-10](https://developers.google.com/search/docs/crawling-indexing/robots/intro)). A `*.farbaek.com` wildcard would keep "office" out of CT logs, but DNS queries, browser history and guessing would still reveal it.

### Supabase redirects and email links need an office-specific path

Keep the project Site URL on www, add exactly `https://office.farbaek.com/auth/callback` to the redirect allow list with no wildcard (Supabase recommends exact paths in production), and give the office its own base-URL setting instead of `NEXT_PUBLIC_SITE_URL` ([Supabase Redirect URLs, accessed Oct 2026](https://supabase.com/docs/guides/auth/redirect-urls)). Email templates are project-wide, so they must build links from `{{ .RedirectTo }}` or `{{ .ConfirmationURL }}` rather than `{{ .SiteURL }}`. Because some mail scanners prefetch and consume `{{ .ConfirmationURL }}`, sending staff a `{{ .Token }}` code avoids that failure and keeps the session minted on the office host ([Supabase email templates, accessed Oct 2026](https://supabase.com/docs/guides/auth/auth-email-templates)). Since staff and customers share one user table, any customer can request a magic link redirected to the office, so reaching the host proves nothing; the staff role check on every request is the boundary. A separate Supabase project for staff identity would isolate identity more strongly, but its cost and wiring were not researched.

### Cloudflare Access is free but costs a DNS migration

Access protects only hostnames in a Cloudflare zone ([Cloudflare self-hosted applications, updated 2026-04-17](https://developers.cloudflare.com/cloudflare-one/applications/configure-apps/self-hosted-apps/)), and on Free and Pro **a full setup is the only option** ([Cloudflare full setup, updated 2026-08-14](https://developers.cloudflare.com/dns/zone-setups/full-setup/)). That means moving farbaek.com's nameservers away from Spaceship and recreating every record, including Spacemail MX, SPF, DKIM and DMARC, Railway's CNAME and TXT records, and the apex redirect. According to search summaries of Cloudflare's docs, partial CNAME setups need Business and single-subdomain delegation needs Enterprise. Railway behind a proxied Cloudflare domain needs SSL mode Full, because "Full (Strict) will not work as intended" ([Railway docs: Working with Domains](https://docs.railway.com/networking/domains/working-with-domains)). That is a production DNS change and therefore the owner's call. A cleaner alternative is a separate registrable domain for the console kept on Cloudflare, which makes the console cross-site to www (so SameSite and cookie-tossing limits apply between them) and leaves farbaek.com's DNS untouched, at the cost of the `office.farbaek.com` name.

## Staff access becomes answerable through an append-only log and tiered data views

### Log who, what, when, why, and the denials

OWASP requires security events to record "when, where, who and what", an interaction identifier linking events, source IP or device, result and reason. Its "always log" list includes privilege changes, every action by application administrators, break-glass use, sensitive-data access and data export, while passwords, tokens, keys, session IDs and sensitive PII "should usually not be recorded directly" ([OWASP Logging Cheat Sheet, undated, accessed Oct 2026](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)). ASVS 5.0 adds synchronized UTC timestamps (16.2.2), logging of failed authorization (16.3.2), logs that "must not be modifiable" (16.4.2) and shipment to a logically separate system so an app breach cannot compromise them (16.4.3) ([OWASP ASVS 5.0 V16](https://raw.githubusercontent.com/OWASP/ASVS/master/5.0/en/0x25-V16-Security-Logging-and-Error-Handling.md)). NIST AU-9(4) and AU-9(6) separate the people who manage the log from those who may read it ([NIST AU-9 via csf.tools](https://csf.tools/reference/nist-sp-800-53/r5/au/au-9/)). Google's own staff-access log is the best real-world model, recording a justification type, a ticket reference, read or write permission type and linked approval IDs for every access by Google personnel ([Google: Understand Access Transparency logs, updated 2026-10-13](https://docs.cloud.google.com/assured-workloads/access-transparency/docs/reading-logs)). Combining these, a Farbaek `staff_audit_events` row needs the fields below.

| Group | Fields |
|---|---|
| When | `occurred_at`, set by the database in UTC; a sequence id |
| Who | `actor_staff_id`, `actor_role`, hashed `actor_session_id`, `auth_strength` (`mfa_fresh` or `step_up`) |
| Elevation and approval | `elevation_grant_id` (JIT), `approval_id` (two-person) |
| Acting as | `on_behalf_of_user_id` for view-as sessions |
| What | namespaced `action` (`account.suspend`, `credits.grant`, `content.view_private`, `staff.role_change`), `target_type`, `target_id`, `workspace_id` |
| Why | `reason_code`, `reason_text`, `ticket_ref` |
| Change | redacted `before` and `after` JSON, secrets reduced to fingerprints |
| Outcome and source | `result` (`success`, `denied`, `error`), `ip`, `user_agent`, `request_id` |
| Visibility and integrity | `customer_visible`, `prev_hash`, `row_hash` |

Atlassian shows the failure mode: user-filed tickets report that its org audit log did not record a support agent's temporary admin access, leaving other admins unaware ([Atlassian ACCESS-2164](https://jira.atlassian.com/browse/ACCESS-2164)). Denials matter as much as successes, because a staff member trying an action their role lacks is a high-value signal. The owner should be alerted immediately on staff role changes, break-glass use, JIT grants to dangerous powers, global kill switches, private-content views without customer consent, bulk exports, credit grants above threshold, bursts of denials, new-country or new-device sign-ins, and any chain break or sequence gap.

### Make the log tamper-evident, not just tamper-resistant

On Supabase Postgres, writes should go only through one `app_record_staff_event` function, UPDATE, DELETE and TRUNCATE should be revoked from every role including `service_role` and backed by a trigger that raises, and each row should be chained with SHA-256 over RFC 8785 canonical JSON, both of which Farbaek already has in `src/core/trust/`. AppMaster's Postgres design supplies the remaining details: order by a sequence number rather than a timestamp, lock the chain head so concurrent writes cannot fork it, and run a read-only verifier that recomputes hashes with `LAG()` and flags broken links and mismatches after deploys, nightly and before audits, recording each run in its own append-only table ([AppMaster: Tamper-evident audit trails in PostgreSQL, 2025-08-29](https://appmaster.io/blog/tamper-evident-audit-trails-postgresql)). Because table owners and superusers can still drop triggers, the verifier is the real backstop, and a daily chain-head export off the database (emailed to the owner, or written to separate write-once storage) meets the intent of ASVS 16.4.3 and NIST AU-9(2) without a SIEM. Supabase-specific `service_role` trigger behaviour was not verified against Supabase docs and should be tested. No standard sets a SaaS-wide retention period for staff logs; the nearest benchmark is PCI DSS 10.5.1, described in secondary sources as **at least 12 months, with the latest 3 months immediately searchable** ([OneUptime, 2026-09-25](https://oneuptime.com/blog/post/2026-09-25-pci-dss-audit-logs-siem-archive-availability/view); [Microsoft Entra PCI Requirement 10](https://learn.microsoft.com/en-ca/entra/standards/pci-requirement-10)). Keeping personal data out of the chained payload, referenced by id instead, lets erasure requests delete that data without breaking the chain.

### Customer content is an exception that needs a reason, and the customer should see it

Leading platforms treat staff access to customer content as a justified exception. Google Access Transparency logs every access by Google personnel with resource, time, reason and accessor details, and Access Approval lets customers approve access in advance ([Google Access Transparency overview, updated 2026-10-13](https://docs.cloud.google.com/assured-workloads/access-transparency/docs/overview)). GitHub's Terms, effective 2026-04-27, limit staff access to private repositories to security, owner-requested support, service integrity, legal compliance and scanning for known violations, and promise that GitHub "will provide notice" except where law bars it, during automated scanning, or under a security threat ([GitHub Terms of Service §E, effective 2026-04-27](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service)). Atlassian runs an "Approve data access" flow ([Atlassian data access FAQ](https://support.atlassian.com/atlassian-cloud/kb/atlassian-cloud-support-data-access-request-faq/)), and Shopify owners approve, deny or edit collaborator requests ([Shopify.dev: Collaborator accounts](https://shopify.dev/docs/storefronts/themes/tools/collaborator-accounts)). ASVS 5.0 requires field-level authorization (8.2.3), and Expertflow's AgentDesk is the anti-pattern, masking PII only in the client so the database and API logs stay unmasked ([Expertflow PII masking 4.9](https://docs.expertflow.com/cx/4.9/pii-data-masking-of-customer-attributes-in-agentde)). Farbaek should mask in the SQL view or server serializer, organised into tiers.

| Tier | What staff see | Gate |
|---|---|---|
| 0, lists and search | Account id, masked email, plan, trial dates, status, usage totals | Any staff role |
| 1, account detail | Full email, recent errors, project names and counts, published URLs | Support and above; view logged |
| 2, private content | Project files, prompts, generated code, conversation history | Reason code plus ticket, customer consent or open abuse case; read-only, about 60 minutes, logged as `content.view_private`, listed to the customer |
| Never | Secret values, customer API keys, env values, OAuth tokens | Fingerprint, last four characters and "set on" date only |

Reason codes can mirror Google's justification set as `CUSTOMER_SUPPORT`, `ABUSE_REVIEW`, `INCIDENT_RESPONSE`, `LEGAL_REQUEST` and `BILLING_SUPPORT`. A modal asking for a reason is not a boundary; the server must find a valid, unexpired access grant before Tier 2 data leaves the database. Each workspace should get a customer-visible "Staff access" list showing when, the staff role, reason code, ticket, what was accessed and for how long, withholding notice only on GitHub-style grounds, plus a default-off, revocable "let support see this project for 24 hours" switch. That list turns an internal control into a reason for customers to trust Farbaek, provided it is never described as certification or compliance.

### View-as should be a read-only rendering mode, never a session swap

The vendor baseline is consistent: a narrow role (Samsara limits impersonation to full admins or a specific custom permission, [Samsara KB](https://kb.samsara.com/hc/en-us/articles/360046654832-Log-in-as-Another-User-User-Impersonation)), read-only by default (Files.com blocks uploads, deletions, share links and settings changes and records activity under the administrator, [Files.com: Impersonate user](https://www.files.com/docs/user-accounts/users/impersonate-user)), notice to the user (Watermark emails users when an admin logs in as them, [Watermark](https://support.watermarkinsights.com/hc/en-us/articles/44525816064539-Administrators-Logging-in-as-another-user)), and both identities on every request (Lightdash tags each request with admin and target, [Lightdash docs](https://docs.lightdash.com/references/workspace/user-impersonation)). Samsara records impersonated actions as the impersonated user, which is the weaker design to avoid. AppMaster's guide lists what to block while impersonating, namely payouts and payment changes, password and MFA changes, exports and "view secret", role grants and ownership changes, account deletion and audit-log removal, and recommends **10-to-15-minute sessions** ([AppMaster: Secure admin impersonation, 2025-12-15](https://appmaster.io/blog/secure-admin-impersonation-controls-audit-scope)). ASVS 8.3.3 requires decisions to use the originating user's permissions rather than the intermediary's.

Farbaek should build "view as" so the staff member keeps their own session while the server renders the customer's views with `viewer = staff` and `subject = customer`, and every write endpoint rejects requests that carry that context. Read-only then becomes a server boundary, not a set of hidden buttons. The mode hard-blocks billing, publish and unpublish, secrets, keys, sign-in, MFA and email changes, invites, exports, deletes, and any AI run that would spend the customer's allowance; shows a non-dismissible banner naming the customer, saying read-only and counting down from 15 minutes with an Exit control; and never targets staff accounts or owners. Most tickets should be answered first from a support view showing build logs, errors, project tree names, usage and plan state, with repairs done through named console actions such as `project.repair_build` that carry their own reason, log entry and customer notice.

## Ten P0 controls cover what mature consoles actually do

GitHub Enterprise Server's site admin is the best-documented public reference: suspension lives in a "Danger Zone" with a required "Log reason", there is a suspended-users list and a Markdown page suspended users see, and suspension keeps all data while blocking sign-in and Git ([GitHub Docs: Suspending users, GHES 3.22](https://docs.github.com/en/enterprise-server@latest/admin/managing-accounts-and-repositories/managing-users-in-your-enterprise/suspending-and-unsuspending-users)). Vercel shows the visitor and owner split, returning `503 DEPLOYMENT_PAUSED` to visitors, emailing owners about policy pauses, and framing a spend-cap pause as "a budget control working as configured rather than a penalty" ([Vercel KB, published 2025-11-03, updated 2026-10-02](https://vercel.com/kb/guide/why-is-my-account-deployment-blocked)). Mapped onto Farbaek's wallets, internal trial, sandboxes, published sites and `not_connected` billing, the sources yield this priority list.

| Priority | Control | Pattern it copies |
|---|---|---|
| P0 | Customer search (Cmd+K) and a customer 360 page: workspaces, trial, wallet ledger, recent runs and cost, sites, flags, staff notes, audit trail | Retool Customer 360 templates; Plain-style event timeline |
| P0 | Suspend and restore with a reason both ways, data kept, enforced in sign-in, API, AI runs, sandbox starts, publish and serving | GHES suspend; Vercel 503 plus owner email |
| P0 | Site takedown that quarantines (neutral disabled page, files and SHA-256 kept as evidence, republish frozen), plus "all sites in workspace" and account suspension | Cloudflare remove-or-disable; Lovable account-level blocking |
| P0 | Abuse intake: abuse@ plus a form with automatic receipt, notice with reasons, appeal path | DSA Arts. 16 and 17; Lovable Platform Rules |
| P0 | Credits as append-only `staff_grant` or `promotional` ledger entries with reason, actor and expiry, never `paid` while billing is `not_connected` | Stripe immutable credit ledger, paid vs promotional category |
| P0 | Named kill switches (`ai_runs`, `sandboxes_start`, `publish`, `serve_published_sites`, `signups`, `trial_starts`, `email_sending`) with owner, reason, audit and a stated fail-safe default | Hodgson ops toggles; Datadog kill switches |
| P0 | Announcement banner (dismissible for notices, fixed during incidents) and honest in-app "paused" reasons | GHES announcement banner |
| P0 | Cost and health tiles labelled estimate or reconciled, plus anomaly alerts | Vercel Spend Management |
| P0 | Pre-billing executive metrics | Lenny activation; a16z cohort rules |
| P0 | Append-only staff audit log with owner alerts | OWASP; ASVS V16 |
| P1 | Capped internal trial extension; erasure with a one-month timer; export; read-only view-as; maintenance scheduling; saved replies | ICO; GDPR Art. 20; GHES maintenance mode |
| P2 | Takedown transparency counts, related-account view, post-publish scanning dashboard, provider-invoice reconciliation | Cloudflare transparency report |

### Account, credit and data-rights controls need ledgers and clocks

Trial extensions should be audited changes to Farbaek's own trial end date (old date, new date, reason, actor, cap), because Stripe's `trial_end` mechanism, capped at 730 days, applies only to provider trials, which Farbaek's rules forbid ([Stripe Docs: Trials](https://docs.stripe.com/billing/subscriptions/trials)). Credits should follow Stripe's model, where "every transaction with credits is recorded in an immutable ledger" ([Stripe blog: credits for usage-based billing](https://stripe.com/jp/blog/introducing-credits-for-usage-based-billing)) and grants carry a `paid` or `promotional` category ([Stripe Docs: Billing credits](https://docs.stripe.com/billing/subscriptions/usage-based/billing-credits)), so Farbaek's `ai_credit_ledger` gains a distinct staff-grant entry type rather than edited balances. Erasure runs on a legal clock: the ICO gives **one month, extendable by two more** with notice inside the first, and allows backup copies to remain until overwritten only if put "beyond use" and disclosed to the person ([ICO: Right to erasure, accessed Oct 2026](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/individual-rights/individual-rights/right-to-erasure/)); published sites count as data made public. Export should be "structured, commonly used and machine-readable" ([GDPR Art. 20](https://gdpr-info.eu/art-20/)), which for Farbaek means a JSON or ZIP of projects, files, contracts and run history, ideally self-serve.

### Abuse handling is a P0 because AI site builders are a phishing magnet

Proofpoint saw "tens of thousands of Lovable URLs detected as threats each month" from February 2025, with one or two prompts producing a working phishing site, and Lovable responded in July 2025 with prompt-time detection and daily scanning of published projects ([Proofpoint, 2025-08-20](https://www.proofpoint.com/us/blog/threat-insight/cybercriminals-abuse-ai-website-creation-app-phishing)). Phishing on Cloudflare Pages rose **198%, from 460 incidents in 2023 to 1,370 by mid-October 2024** ([Fortra, Oct 2024](https://www.fortra.com/blog/cloudflares-pagesdev-and-workersdev-domains-increasingly-abused-phishing)). The EU Digital Services Act imposes duties on every hosting provider regardless of size: Art. 16 requires an easy electronic notice mechanism, confirmation of receipt and decisions that are "timely, diligent, non-arbitrary and objective" ([SpringLex: DSA Art. 16](https://www.springlex.eu/en/packages/dsa/dsa-regulation/article-16/)), and Art. 17 requires "a clear and specific statement of reasons" to affected users when content is restricted or an account suspended ([StreamLex: DSA Art. 17](https://streamlex.eu/articles/dsa-en-art-17/)). Netlify forum reporters complain that taking down one URL fails when the abuser redeploys on the same account ([Netlify forum](https://answers.netlify.com/t/urgent-abuse-report-suspected-scam-lending-website-hosted-on-netlify/168064)), so account-level action must exist from day one. Farbaek already serves user sites from the separate registrable domain `farbaek.si`, the github.io pattern GitHub adopted in 2013 for cookie and phishing reasons ([GitHub blog, 2013](https://github.blog/news-insights/the-library/new-github-pages-domain-github-io/)). Every `*.farbaek.si` site still shares one site with the others, so an owner-requested listing in the Public Suffix List's PRIVATE section ([publicsuffix.org](https://publicsuffix.org/submit/)) would isolate them from each other, and Heroku-style random suffixes would make lookalike names harder ([Heroku blog](https://www.heroku.com/blog/mitigating-subdomain-reuse/)).

### Kill switches must fail in a stated direction and explain themselves

Pete Hodgson's "Ops Toggles" must be reconfigurable without a deploy, some serve long-term as "a manually managed circuit breaker", and each needs an owner because toggles carry a cost ([Feature Toggles, martinfowler.com, revised 2017-10-09](https://martinfowler.com/articles/feature-toggles.html)). Datadog's example keeps the feature on when the flag store is unreachable ([Datadog: Kill switches](https://docs.datadoghq.com/feature_flags/use_cases/kill_switches/)), while Farbaek's fail-closed rule points the other way for security-relevant switches, so the default should be recorded per switch. GHES adds mandatory messages that log an audit event for each version a user acknowledged, announcement banners, and maintenance mode scheduled at least 30 minutes ahead ([GitHub Docs: Customizing user messages](https://docs.github.com/en/enterprise-server@latest/admin/managing-accounts-and-repositories/communicating-information-to-users-in-your-enterprise/customizing-user-messages-for-your-enterprise); [GHES 3.1 maintenance mode](https://docs.github.com/en/enterprise-server@3.1/admin/configuration/configuring-your-enterprise/enabling-and-scheduling-maintenance-mode)). When a switch is off, the matching control in the customer app must say why, which is Farbaek's "no dead ends" rule applied to operations.

### Buy the inbox, build the customer page, and label every cost figure

Ticketing is not worth building. Help Scout's reported free tier (five users, one inbox) is contested, with one 2026 aggregator saying it no longer exists ([Unthread, 2026](https://unthread.io/blog/help-scout-pricing/); [Dupple](https://dupple.com/pricing/help-scout)), so verify before relying on it; Plain's Events API shows how product events can later flow into support threads ([Plain docs: Events](https://www.plain.com/docs/graphql/events)), and Stripe's "Support Communications" role, which manages support requests and nothing else, models a support seat ([Stripe roles](https://docs.stripe.com/get-started/account/teams/roles)). For cost, Vercel's Spend Management sets the norm of alerts at **50%, 75% and 100%**, an optional pause and a webhook, while admitting that checks are not continuous and actions can fire "several minutes after" the threshold ([Vercel Docs: Spend Management](https://vercel.com/docs/spend-management)). Farbaek's tiles should show AI spend today, over seven days and month to date by provider, model and operation (computed from `src/config/usage.ts` and the rate card), sandbox time and estimated cost, the top ten spending workspaces, cost per active workspace, trial wallets near zero and run failure rates by error class. Each tile should say whether its figure is an estimate or reconciled, as ADR 0026 already does by labelling AI cost as list cost, with provider-side limits such as Anthropic's per-workspace spend limits ([Anthropic: Workspaces](https://anthropic.com/news/workspaces)) as a backstop to Farbaek's own metering.

### CEO metrics must stay honest while billing is not connected

Lenny Rachitsky's survey defines activation as the earliest user-level milestone that predicts retention, with a **SaaS median of 30%** ([Lenny's Newsletter, 2022-10-25](https://www.lennysnewsletter.com/p/what-is-a-good-activation-rate)), and a16z insists that cohort charts be non-cumulative because "cumulative charts always rise" and that "active" be defined explicitly ([a16z: 16 Startup Metrics, 2015-08-21](https://a16z.com/16-startup-metrics/)). A pre-billing executive view should therefore track sign-ups; activation, proposed as approving an intent contract and reaching a verified result or a published site within seven days, then validated against week-4 retention; weekly active workspaces with at least one run, approval or publish; week 1, 4 and 8 cohorts; live published sites; AI cost per active workspace; and the trial funnel. MRR, ARR, trial-to-paid, churn and gross margin show as visibly unavailable ("Billing not connected") until go-live. When billing arrives, two benchmarks matter and both are contested. No-card trial conversion medians sit at 4 to 6% in ChartMogul's 2026 data (via Userpilot) against an 18.2% FirstPageSage average ([Userpilot, accessed Oct 2026](https://userpilot.com/blog/free-trial-conversion-rate/)). AI gross margins run well below classic SaaS: a16z found AI companies "often in the 50-60% range" in 2020 ([a16z: The New Business of AI, Feb 2020](https://a16z.com/the-new-business-of-ai-and-how-its-different-from-traditional-software/)), and Bessemer's August 2025 report puts fast-scaling "Supernovas" near 25% ([Bessemer report mirror, Aug 2025](https://openlinksw.com/data/html/bessemer-ventures-ai-2025-report-claude.html)), so inference and sandbox costs belong in cost of revenue from the start.

## Calm consoles dim the chrome and grade friction by risk

### Quiet navigation, one palette, and entity pages with timelines

The 2026 leaders moved in the same direction. Vercel made a resizable, hideable sidebar the default on 2026-02-26, ordered by most common workflow, with a floating bottom bar on mobile "designed for one-handed use" ([Vercel changelog, 2026-02-26](https://vercel.com/changelog/dashboard-navigation-redesign-rollout)). Linear's March 2026 refresh made the sidebar "a few notches dimmer", softened dividers on the principle that "Structure should be felt not seen", and cut icons, reducing the density of the chrome while keeping content dense ([Linear: A calmer interface, 2026-03-12](https://linear.app/now/behind-the-latest-design-refresh)). The command palette is the keyboard spine: Superhuman recommends one shortcut that works and closes everywhere, every action available as a command with its shortcut shown, fuzzy matching and context boosting ([Superhuman blog, 2021-10-12](https://blog.superhuman.com/how-to-build-a-remarkable-command-palette/)). For Farbaek it should also jump straight to entities from id prefixes like `ws_`, with a visible search button kept for non-power users like the CEO. Attio's May 2026 record page provides the entity model, with identity and primary actions top-left "where the eye lands first" and a filterable activity timeline that collapses automation noise by default ([Attio changelog, 2026-05-28](https://attio.com/changelog/2026/record-page-redesign); [Attio timeline, 2026-06-29](https://attio.com/changelog/2026/new-activity-timeline)). NN/g adds that a table's first column should be a readable name rather than an id, and that records should open in a side panel rather than a modal ([NN/g: Data Tables, 2022-04-03](https://www.nngroup.com/articles/data-tables/)).

### Glanceable numbers, discrete density, and status that never relies on colour

Keep the overview to about five KPIs, each with an arrow-and-sign delta and a seven- or 30-day sparkline with the latest point marked ([Smashing Magazine, 2025-09-12](https://www.smashingmagazine.com/2025/09/ux-strategies-real-time-dashboards/)); use bars for comparison and lines for trends, with no pies or gauges ([NN/g: Dashboards, 2017-06-18](https://www.nngroup.com/articles/dashboards-preattentive/)). Carbon's discrete row heights of 32, 40 and 48 px give a clean density toggle ([Carbon data table, updated 2026-09-30](https://carbondesignsystem.com/components/data-table/usage/)), and Carbon states that "relying solely on color to convey status is insufficient", asking for at least three of symbol, shape, colour and text at 3:1 contrast ([Carbon status indicators, updated 2026-08-12](https://carbondesignsystem.com/patterns/status-indicator-pattern/)). Farbaek's existing `verified`, `approval`, `failed`, `info` and `unverified` tokens already form that status set. Times should read relative with the exact time on hover, switching to absolute dates after 30 days ([Primer RelativeTime](https://primer.style/product/components/relative-time/)). Empty states must say why they are empty and what to do next ([NN/g: Empty states, 2021-09-19](https://www.nngroup.com/articles/empty-state-interface-design/)), so a revenue tile reads "No payments yet: billing is not connected" instead of $0. Live panels carry a Live, Stale or Paused pill with an "as of" time, and ids, hashes and timestamps use Geist Mono.

### Friction should scale with harm, and only the harmful direction is gated

| Tier | Example office actions | Pattern |
|---|---|---|
| 1, reversible | Add a note, reassign, mute an alert | Act at once, toast with Undo for 5 to 10 s; optimistic UI allowed |
| 2, costly | Suspend a workspace, take down a site, grant credits | Dialog naming the entity and its effects, outcome-labelled buttons ("Suspend acme" / "Keep active"), required reason |
| 3, severe | Delete customer data, bulk export, change roles, global kill switch | Danger zone, typed entity name, fresh MFA step-up, second-person approval where the matrix requires it |

Cloudscape reserves typed confirmation for "serious, irreversible or cascading consequences" ([Cloudscape delete patterns, 2020-06-05](https://cloudscape.design/patterns/resource-management/delete/)). NN/g warns that overused confirmations breed reflexive clicking, asks for outcome-labelled buttons and cites a second person for the most dangerous actions ([NN/g: Confirmation dialogs, 2018, reviewed 2026-08-07](https://www.nngroup.com/articles/confirmation-dialog/)). GitHub's sudo mode re-authenticates high-impact actions within a two-hour window ([GitHub Docs: Sudo mode](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/sudo-mode)); Farbaek's five-minute, action-bound step-up is deliberately stricter because the console holds the service role. Vercel gates pausing a project behind a typed name but resumes it without confirmation, an asymmetric friction worth copying ([Vercel Docs: Managing projects, updated 2026-08-11](https://vercel.com/docs/projects/managing-projects)). AWS Multi-party approval has verified each approver's vote with a one-time code since February 2026, so identity admins cannot impersonate approvers ([AWS What's New, Feb 2026](https://aws.amazon.com/about-aws/whats-new/2026/02/aws-multi-party-approval-requires-one-time-password-verification-for-voting)). Optimistic UI belongs only in Tier 1, because React notes a failed optimistic update rolls back silently unless the error is reported ([React useOptimistic](https://react.dev/reference/react/useOptimistic)). Under the one-accent rule, destructive buttons cannot be signal blue; they use the `failed` token with a warning icon and explicit wording.

### Make the security state impossible to miss, then make it accessible

AWS colours the whole navigation bar per account ([AWS What's New, Aug 2025](https://aws.amazon.com/about-aws/whats-new/2025/08/aws-management-console-assigning-color-aws-account)), which White Signal rules out, so Farbaek should use a labelled environment pill (Production or Staging) with an icon and a hatched band in the header and in every Tier 3 dialog, a role badge beside the avatar, the non-dismissible view-as banner, an elevation countdown chip, and disabled controls that state their reason ("Needs Admin"). WCAG 2.2.1 requires a warning at least 20 seconds before an inactivity timeout and a simple way to extend ([W3C Understanding 2.2.1, updated 2026-08-10](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html)), so the idle timer should warn with a one-click "Stay signed in", while the 12-hour absolute limit is a security cap whose tension with that criterion should be acknowledged rather than hidden. Motion should signal something: feedback within 100 to 150 ms, KPI value changes over 200 to 400 ms and list reorders under 300 ms ([NN/g: Animation in UX, 2020-01-12](https://www.nngroup.com/articles/animation-purpose-ux/); [Smashing, 2025-09-12](https://www.smashingmagazine.com/2025/09/ux-strategies-real-time-dashboards/)); no loading indicator under one second, and a spinner for one card or a skeleton for a full page at two to ten seconds ([NN/g: Skeleton screens, 2023-06-04](https://www.nngroup.com/articles/skeleton-screens/)); and opacity cross-fades in place of movement under reduced motion ([W3C Understanding 2.3.3](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)). On phones, follow Linear's "away from keyboard" companion model rather than shrinking the console ([Linear Mobile, 2024-09-19](https://linear.app/changelog/2024-09-19-introducing-linear-mobile)): the CEO gets KPI tiles, an approvals and alerts inbox with 44 px approve and decline pills, search, and read-only entity summaries, while Tier 3 actions show as visibly unavailable on mobile with a reason. Dense consoles most often fail WCAG 2.5.8's 24 px target minimum ([W3C 2.5.8, updated 2026-05-11](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)), 2.4.11 when sticky headers and banners hide focus, which `scroll-padding` fixes ([W3C 2.4.11, updated 2026-06-15](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)), 2.5.7 when an interaction is drag-only ([W3C 2.5.7, updated 2026-08-10](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)), and 2.2.1 on timeouts. A 2 px focus ring at 3:1 meets the AAA focus-appearance bar cheaply ([W3C 2.4.13, updated 2026-09-06](https://www.w3.org/WAI/WCAG22/Understanding/focus-appearance.html)).

## Conclusion

Sequencing matters more than the feature list. Today's read-only `/admin` is defensible behind a magic link precisely because it cannot change anything; the first write button removes that defence, so `aal2` MFA, the server-only staff table and the append-only log have to land before any write action, not alongside it. A less obvious lesson is that at Farbaek's current plan tiers most of the console's real security must live in its own code. Supabase gates session limits behind Pro, account lockout hooks behind Team and keeps auth logs for an hour on Free; Railway offers no inbound allowlist and no documented client-IP guarantee; Cloudflare Access is free only after a DNS migration. The robust design therefore duplicates each platform control in Farbaek's own server and database (`staff_sessions`, per-account lockout, an off-database chain head, the Origin check), so paid plans add defence in depth instead of being the only defence, and Farbaek's existing canonical JSON and SHA-256 code in `src/core/trust/` and its service-role-only `app_*` path already supply most of the parts.

Four uncertainties need staging tests before anything depends on them: whether Supabase passkey sign-in yields `aal2`, whether `mfa.verify()` refreshes the `amr` timestamp, how `service_role` interacts with the audit triggers, and what Railway actually puts in its forwarding headers. Three decisions belong to the owner because they touch money or production: a second Railway service (recommended) versus Railway Pro, Supabase Pro for session controls and longer auth logs, and whether to move DNS to Cloudflare for Access or give the console its own domain. The customer-visible staff access log is worth building early, because it turns an internal safeguard into something customers can see and trust, as long as it is never described as certification or compliance.
